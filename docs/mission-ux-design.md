# Mission Initialization and Launch UX

## Status

Implemented for work package 12, with live operator-project acceptance pending.
The fixed two-agent launcher in `scripts/launch-dogfood-herdr.sh` validated the
Herdr mechanics; `/mycelial init`, `agent_mission_read`, optional role preset
metadata, and generated per-mission launchers now provide the generic workflow.

## Problem

The durable mailbox works independently of an orchestrator, but current setup
requires users to create several control files and issue one Pi/Herdr launch
command per role. The first dogfood run showed that durable coordination works;
it also showed that per-agent launch ceremony should not be the normal user
experience.

A user should be able to finish a discovery conversation, approve mission
creation, and run one inspectable launcher. Mycelial must improve that workflow
without turning mailbox runtime code into a process supervisor.

## Decisions

### Mission location

The default root is:

```text
~/mycelial/missions/<mission-id>/
```

One directory per mission preserves concurrent and historical missions while
keeping the product name visible and memorable. An explicitly configured
`missionRoot` still takes precedence.

### Mission authorship

`mission.md` is human-owned or human-approved. An LLM may draft it during a
discovery conversation, but creation remains an explicit operator action.
Repository `AGENTS.md` remains authoritative and cannot be overridden by a
mission document.

### Pi command as approval boundary

Register `/mycelial` even when the current Pi process has no mission binding.
The initial workflow is:

```text
/mycelial init <mission-id> --roles <role,...> [--from <source.md>] [--no-coordinator]
```

With `--from`, the command treats a user-approved repository Markdown file as a
canonical source artifact and generates a mission wrapper that references it.
It does not duplicate the source into mission storage. Without `--from`, the
command generates a minimal editable template. It validates identifiers,
refuses implicit overwrite, creates the mission directory, and reports every
output path. It does not launch processes itself.

At minimum it generates:

```text
~/mycelial/missions/<mission-id>/
  mission.md
  agents.json
  repos.json
  launch-herdr.sh
```

It also creates a non-overwriting project shortcut:

```text
<repository>/launch-mycelial-<mission-id>.sh -> ~/mycelial/missions/<mission-id>/launch-herdr.sh
```

If `<repository>/AGENTS.md` is absent, initialization creates a non-overwriting
minimal scaffold at that exact path. It never searches for substitutes and
never modifies an existing `AGENTS.md`; repository-specific commands and policy
remain operator-owned.

The mission-specific launcher name avoids collisions when one repository participates in multiple missions. The command reports both paths and the guidance path, and leaves repository ignore policy to the operator.

The command records the repository cwd in the generated launcher for the first
version. Cross-repository launch placement is a later extension; `repos.json`
aliases remain message metadata until a path schema is deliberately designed.

### Explicit mission reading

Add `agent_mission_read` with no model-facing identity or path arguments. It
uses the trusted runtime binding to resolve and return bounded `mission.md`
content. The package skill calls it during startup, followed by roster refresh
and mailbox read.

Mission content is loaded explicitly rather than injected into every turn. This
keeps context use visible and prevents a model from selecting another mission
path.

### Coordinator and role launch metadata

Initialization prepends `coordinator` unless it was explicitly listed or the
operator passes `--no-coordinator`. The generated mission gives that role
concrete decomposition, routing, blocker-tracking, and acceptance
responsibilities. Other configured roles receive generic claim-and-report
responsibilities that the coordinator specializes through durable requests.
Role identity still does not infer a persona or model.

Continue accepting the simple role array:

```json
{
  "agents": ["coordinator", "implementer", "reviewer"]
}
```

Also support an object keyed by role when launch metadata is needed:

```json
{
  "coordinator": {},
  "reviewer": {
    "preset": "domain-auditor"
  }
}
```

Role remains the Mycelial identity. A preset is optional launcher metadata, not
an inferred identity. For the example above the launcher passes both:

```text
--mycelial-role reviewer --presets:preset domain-auditor
```

Mycelial does not select models, providers, thinking levels, or persona policy.
Those remain Pi and pi-presets responsibilities.

### Generated Herdr launcher

`launch-herdr.sh` is generated by Mycelial, inspected or edited by the user, and
executed explicitly from a Herdr-managed control shell. It must:

1. Validate Herdr context and required local commands.
2. Leave the invoking control tab intact.
3. Launch every configured role when no role arguments are supplied.
4. Accept role arguments to launch only a selected subset.
5. Open one Herdr tab per selected role and locate its initial shell pane.
6. Use the role as the default Herdr agent name.
7. Start Pi with trusted mission and role flags.
8. Forward `--presets:preset` only when configured for that role.
9. Prompt the coordinator first and wait for it to create durable initial
   assignments without issuing initial wake-ups.
10. Prompt workers to read and claim those assignments without waiting for their
    implementation turns to complete.
11. Report mission, role, tab, pane, and agent identifiers.
12. Be reachable through the generated mission-specific project symlink.
13. Fail visibly on name collisions or partial startup and leave created tabs
    available for inspection.

Generated values must be validated and shell-quoted. The launcher must not
silently overwrite mission data, close user tabs, or hide failed starts.

Launching all roles by default is intentional: `agents.json` declares the
mission participants. Subset selection supports staged startup and recovery.

## Live wake-up boundary

Mission launch automation is distinct from durable mailbox storage. The bound
`agent_wake` tool provides a narrow best-effort adapter: after durable send or
reply succeeds, it validates one direct recipient against the mission roster and
invokes the role-named Herdr agent with a fixed notification containing no task
content. It rejects self-targets and does not accept model-provided prompt text.
Wake failure never rolls back or invalidates mail.

The launcher handles the initial coordinator-to-worker notification itself, so
the coordinator is told not to wake workers during its startup turn. Mycelial
does not become a resident supervisor or add receiver-side polling.

## Dogfood evidence

The two-agent message-ordering mission established that:

- opening one Herdr tab per role and starting bound Pi agents works;
- matching Herdr names to Mycelial roles is sufficient for an initial mapping;
- scripted startup and wake-ups remove per-agent operator ceremony;
- durable send, read, acknowledgement, claim, reply, done, and release complete
  successfully across processes;
- direct Bun commands are unsuitable inside the agent sandbox, while a
  Node-backed `just check` succeeds;
- Herdr prompt completion alone is not a mission verdict, so durable state and
  final agent output must remain distinguishable.

## Acceptance criteria

WP12 is complete when a user can:

1. Conduct a discovery conversation and approve one `/mycelial init` command.
2. Review or edit the generated mission files and launcher.
3. Run one launcher from a Herdr control shell.
4. See the default coordinator create initial assignments before workers are
   prompted in separate tabs with correct trusted bindings and optional presets.
5. Have each agent explicitly read its mission and referenced source artifact
   without a path-heavy startup prompt.
6. Initialize a repository without `AGENTS.md` and receive a non-overwriting
   scaffold, while preserving an existing file unchanged.
7. Wake another configured role through `agent_wake` only after durable mail.
8. Remove Herdr and still use the durable mailbox with manually launched Pi
   sessions.
